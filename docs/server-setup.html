Putting FriendsChat on your own server

A checklist for after someone hands you SSH access to an AWS machine. Written so you can follow it yourself — though you can also ask Claude to do any step with you. Read what each command does before running it: on your own server there is no undo button.

The short answer to your question. One machine runs everything — the app, the database, and the web server that provides HTTPS. You do not need Render, Neon, or any other hosting service. Two things still live outside it: a domain name (about £10/year) for a real web address, and backups, which must be copied off the machine or they die with it.

00What to ask for

When the person buying the server asks what you need, this is the answer:

SettingAsk forWhy it matters
ServiceAWS Lightsail, not EC2Same machine underneath, far simpler screens and a fixed monthly price
Size1 GB RAM, about $7/moThe $5 / 512 MB plan runs out of memory during installs
SystemUbuntu 24.04 LTS“LTS” means security support for years, and it is the most documented choice
RegionNearest you and your friendsShorter distance, faster messages
Static IPYes — attach oneWithout it the address changes on reboot and your link breaks
AccessThe .pem key file and usernameYour key to the door. The user is normally ubuntu.

About wanting root and a normal user. Ubuntu gives you one normal user (ubuntu) who becomes root on demand with sudo. That is the safe arrangement — logging in directly as root is how servers get destroyed by one mistyped command. If you are handed a root password, step 03 turns that login off.

01Protect the key, then log in

You will be given a file like friendschat.pem. It is the password to the machine — anyone holding it can log in as you. Never email it, never commit it to GitHub.

mkdir -p ~/.ssh
mv ~/Downloads/friendschat.pem ~/.ssh/
chmod 600 ~/.ssh/friendschat.pem   # only you can read it

ssh -i ~/.ssh/friendschat.pem ubuntu@YOUR.SERVER.IP

SSH refuses to use a key other people on the computer could read — that is what chmod 600 fixes. The first connection asks whether to trust the machine; type yes. It is recording a fingerprint so it can warn you if you ever reach an impostor later.

To stop typing all that, add this to ~/.ssh/config on your Mac and afterwards just run ssh friendschat:

Host friendschat
  HostName YOUR.SERVER.IP
  User ubuntu
  IdentityFile ~/.ssh/friendschat.pem

02Update everything

sudo apt update && sudo apt upgrade -y

This pulls the latest security fixes, and repeating it every few weeks is the single most important habit for keeping a server safe. If it tells you a reboot is required, run sudo reboot, wait a minute, and connect again.

03Lock the front door

Machines on the internet start receiving automated break-in attempts within minutes of going live. Three defences, in order:

# 1 — firewall: allow only SSH and web traffic
sudo ufw allow OpenSSH
sudo ufw allow 80,443/tcp
sudo ufw enable

# 2 — keys only, no passwords, no root
sudo nano /etc/ssh/sshd_config

Make these three lines read exactly this, then save with Ctrl+O, Enter, Ctrl+X:

PermitRootLogin no
PasswordAuthentication no
PubkeyAuthentication yes
sudo systemctl restart ssh

# 3 — ban repeated failed attempts automatically
sudo apt install -y fail2ban
sudo systemctl enable --now fail2ban

Keep this terminal open. Open a second terminal and confirm you can still log in. If you have just locked yourself out, the window still open is how you undo it. If both are closed, use Lightsail’s browser console to get back in.

04Install the software

# Node.js 20 — the app needs 18 or newer
curl -fsSL https://deb.nodesource.com/setup_20.x | sudo -E bash -
sudo apt install -y nodejs

# PostgreSQL — the database that survives restarts
sudo apt install -y postgresql

# Nginx — terminates HTTPS and forwards to the app
sudo apt install -y nginx

node -v && psql --version && nginx -v   # all three should answer

05Create the database

sudo -u postgres psql

That opens the database’s own prompt. Type these four lines, choosing a long random password and writing it down — step 06 needs it:

CREATE DATABASE friendschat;
CREATE USER friendschat WITH PASSWORD 'your-long-random-password';
GRANT ALL PRIVILEGES ON DATABASE friendschat TO friendschat;
\q

By default Postgres listens only to programs on this same machine, not to the internet. That is exactly what we want, so there is nothing to change.

06Put the app on the server

cd ~
git clone https://github.com/bellaw838/friendchat.git
cd friendchat
npm install --omit=dev

nano ~/friendchat/.env
NODE_ENV=production
PORT=3000
DATABASE_URL=postgres://friendschat:your-long-random-password@localhost:5432/friendschat
SESSION_SECRET=paste-a-long-random-string

Generate that secret with openssl rand -hex 32. It signs the login cookies, so if it leaks someone could forge logins. The .env file never goes into GitHub.

One prerequisite is not built yet. The app still stores data in a SQLite file, so DATABASE_URL does nothing until the Postgres rewrite is done — that is the “Phase 1” work to ask Claude for. Everything else on this page works today, and the rewrite changes only src/db.js.

07Keep it running forever

Typing npm start means the app dies the moment you close the terminal. This registers it as a system service instead — started at boot, restarted after a crash:

sudo nano /etc/systemd/system/friendschat.service
[Unit]
Description=FriendsChat
After=network.target postgresql.service

[Service]
Type=simple
User=ubuntu
WorkingDirectory=/home/ubuntu/friendchat
EnvironmentFile=/home/ubuntu/friendchat/.env
ExecStart=/usr/bin/node src/server.js
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
sudo systemctl daemon-reload
sudo systemctl enable --now friendschat
sudo systemctl status friendschat        # expect "active (running)"

Two commands worth memorising: sudo systemctl restart friendschat after changing code, and journalctl -u friendschat -f to watch the live log when something misbehaves.

08A real address, with HTTPS

Buy a domain (Namecheap or Cloudflare, roughly £10/year) and point an A record at your server’s IP. Then put Nginx in front of the app:

sudo nano /etc/nginx/sites-available/friendschat
server {
    server_name yourdomain.com;
    client_max_body_size 20M;   # room for 10 MB videos

    location / {
        proxy_pass http://localhost:3000;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;    # these two lines
        proxy_set_header Connection "upgrade";     # keep live chat alive
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
sudo ln -s /etc/nginx/sites-available/friendschat /etc/nginx/sites-enabled/
sudo rm -f /etc/nginx/sites-enabled/default
sudo nginx -t && sudo systemctl reload nginx

# free certificate, renews itself
sudo apt install -y certbot python3-certbot-nginx
sudo certbot --nginx -d yourdomain.com

The two lines everyone forgets. Without the Upgrade headers the page loads perfectly but messages never arrive live — because the WebSocket connection that carries chat gets dropped at the proxy. If FriendsChat ever loads but feels dead, look here first.

09Backups — the step people regret skipping

A backup stored on the same machine dies with the machine. This keeps fourteen days of history locally, and you copy them to your Mac regularly:

mkdir -p ~/backups
nano ~/backup-db.sh
#!/bin/bash
export PGPASSWORD='your-long-random-password'
pg_dump -U friendschat -h localhost friendschat \
  | gzip > ~/backups/friendschat-$(date +%F).sql.gz
find ~/backups -name '*.sql.gz' -mtime +14 -delete
chmod +x ~/backup-db.sh
crontab -e
# add this line — 3am nightly
0 3 * * * /home/ubuntu/backup-db.sh

Then from your Mac, pull copies down:

scp -i ~/.ssh/friendschat.pem 'ubuntu@YOUR.SERVER.IP:~/backups/*.gz' ~/Desktop/

A backup you have never restored is only a hope. Once, open one and check it contains real data: zcat friendschat-2026-08-15.sql.gz | head -40.

10Set a billing alarm today

In the AWS console: Billing → Budgets → Create budget. Set a monthly limit near your expected cost with an email alert. Lightsail is a fixed price, so this is really a tripwire for anything accidentally left running elsewhere in the account. Do it on day one, not after the first surprise.

When something breaks

What you seeWhere to look
Nothing loadssudo systemctl status friendschat, then journalctl -u friendschat -n 50
502 Bad GatewayNginx is up but the app is down — restart it and read the log
Loads, but no live messagesThe two Upgrade lines in the Nginx config
Everyone logged outSESSION_SECRET changed, or Postgres is not running
Locked out of SSHLightsail console → “Connect using SSH” in the browser
Disk fulldf -h, then clear old backups and sudo apt clean

Your ongoing jobs

  • Every few weeks — sudo apt update && sudo apt upgrade -y
  • Monthly — copy backups to your Mac, and open one to confirm it holds real data
  • Yearly — renew the domain before it expires
  • Never — share the .pem key, or commit .env to GitHub

Owning the machine means owning the problems. That is the trade you chose, and it is a genuinely good way to learn how the internet actually works. Nothing here is beyond you — just take the steps in order, and keep that second terminal open during step 03.
